# Upgrade

JumpServer has two upgrade paths. Choose the one that matches the edition and
installation method used for the deployment.

| Edition            | Upgrade method   | Package source           |
| ------------------ | ---------------- | ------------------------ |
| Community Edition  | Online installer | GitHub releases          |
| Enterprise Edition | Offline package  | JumpServer delivery team |

<Alert type="warning">
  An upgrade restarts services and can interrupt active sessions. Plan a
  maintenance window, notify users, and create a verified database backup before
  you begin. See [Backup & Restore](/operations/maintenance/backup-restore).
</Alert>

## Before you begin

- Read the [changelog](/reference/changelog) and release notes for the target
  version, including database and Redis requirements.
- Confirm the supported upgrade path in
  [Upgrade & Maintenance](/operations/maintenance/upgrade-maintenance).
- Back up the database and the active configuration with
  `./jmsctl.sh backup_db`; copy the backup off the host.
- Keep the current installation package and configuration until the new version
  has been verified.
- Run the commands as `root` or a user with superuser privileges.

## Community Edition: online upgrade

Use this path when JumpServer was installed with the online one-line installer and
the server can reach GitHub.

<Steps>

<div>Change to the `/opt` directory. ```sh cd /opt ```</div>

<div>
  Download the installer package for the target version.
  <VersionedCommand template="wget https://github.com/jumpserver/installer/releases/download/{version}/jumpserver-installer-{version}.tar.gz" />
</div>

<div>
  Extract the package.
  <VersionedCommand template="tar -zxvf jumpserver-installer-{version}.tar.gz" />
</div>

<div>
  Change to the extracted directory.
  <VersionedCommand template="cd jumpserver-installer-{version}" />
</div>

<div>Run the upgrade. ```sh ./jmsctl.sh upgrade ```</div>

<div>Start the services. ```sh ./jmsctl.sh start ```</div>

</Steps>

## Enterprise Edition: offline package upgrade

Use this path when JumpServer was installed from an Enterprise offline package.
The package is provided by the JumpServer delivery team and does not require
internet access on the target server.

<Steps>

<div>
  Obtain the Enterprise upgrade package and confirm that its version and CPU
  architecture match the target deployment.
</div>

<div>Change to the `/opt` directory. ```sh cd /opt ```</div>

<div>
Place the offline package in `/opt`. Upload it from the delivery portal, or use
`wget` when the server can reach the download URL.

<Tabs>
  <Tab label="Upload">
    <Steps stepLevel="2">
      <div>
      Download the package from the offline package site provided by the delivery
      team.
      </div>

      <div>
      Upload the package to `/opt` on the deployment server.
      </div>
    </Steps>

  </Tab>

  <Tab label="wget">
    <Steps stepLevel="2">
      <div>
      Copy the package download link from the delivery portal.
      </div>

      <div>
      Replace `YOUR_DOWNLOAD_URL` with the copied link and download the package.
      <VersionedCommand template={'cd /opt && wget -O jumpserver-ee-{version}-x86_64.tar.gz "YOUR_DOWNLOAD_URL"'} />
      </div>
    </Steps>

  </Tab>
</Tabs>

</div>

<div>
  Extract the package.
  <VersionedCommand template="tar -zxvf jumpserver-ee-{version}-x86_64.tar.gz" />
</div>

<div>
  Change to the extracted directory.
  <VersionedCommand template="cd jumpserver-ee-{version}-x86_64" />
</div>

<div>
  Run the upgrade. The default options are sufficient for a standard deployment.
  ```sh ./jmsctl.sh upgrade ```
</div>

<div>Start the services. ```sh ./jmsctl.sh start ```</div>

</Steps>

## After the upgrade

1. Check the service state:
   ```sh
   ./jmsctl.sh status
   ```
2. Sign in and confirm the version shown in the UI.
3. Verify that users can open sessions and that recent recordings and audit logs
   are still available.
4. For Enterprise Edition, confirm that the license is still valid. If needed,
   import it again from [License](/reference/license).
5. Review the Core and component logs for errors:
   ```sh
   ./jmsctl.sh tail core
   ```
6. If the upgrade fails, stop the services and restore the backup from
   [Backup & Restore](/operations/maintenance/backup-restore).

## Version-specific upgrade notes

These notes describe the behavior changes and fixes in each target version. They do not change the upgrade commands in the preceding sections.

### JumpServer v5.1.0

<VersionBadge version="5.1.0" kind="changed" />

| Change                                                                                                 | What to check after the upgrade                                                                                                                                     |
| ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| OpenBao enables HTTPS by default                                                                       | Verify the OpenBao certificate and CA configuration, and update clients that connect to OpenBao directly. See [Security hardening](/operations/security/security-hardening). |
| DBX replaces DBeaver as the default remote database application                                        | Confirm that database sessions in Luna Workspace open with DBX. See [Connection settings](/user-guide/client/connection-settings).                                    |
| Tinker provides standalone RDP desktops through the Windows authentication plugin instead of RemoteApp | Review published Windows applications and the Tinker hosts that serve them. See [RemoteApp](/administration/system-settings/infrastructure/remote-app).                                  |
| MFA user settings follow the system configuration by default                                           | Confirm the system-level MFA policy before users sign in. See [Authentication](/administration/system-settings/security/authentication).                                           |
| KoKo TUI restores the plain-text connection mode                                                       | Review terminal access for direct SSH connections. See [SSH Terminal](/user-guide/workbench/ssh-terminal).                                                            |

### JumpServer v5.1.1

<VersionBadge version="5.1.1" kind="changed" />

| Change                                                                                                                                               | What to check after the upgrade                                                                                                                                            |
| ---------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| High availability deployments apply stronger persistent write protection to databases and Redis                                                      | Confirm that databases and Redis keep working after container restarts, re-creation, and failure recovery. See [Deployment topologies](/operations/deployment/deployment-topologies). |
| Redeployment and switchover checks tolerate normal replication lag                                                                                   | Confirm that redeployment and switchover finish without false failure reports. See [Deployment topologies](/operations/deployment/deployment-topologies).                             |
| Access Token format validation preserves fallback compatibility with other Bearer Token authentication methods                                       | Verify API clients that authenticate with Bearer tokens. See [Access keys](/user-guide/general/account/access-keys).                                                                 |
| Tinker applet host deployment checks Group Policy, disables listener NLA before installation, and stops with guidance when Group Policy requires NLA | Review the deployment result for Tinker hosts. See [RemoteApp](/administration/system-settings/infrastructure/remote-app).                                                                      |
