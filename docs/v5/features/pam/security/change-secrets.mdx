# Change Secrets

<Alert type="xpack">
**Change Secrets** requires JumpServer Enterprise Edition. Without a license, the Security > Change Secrets tabs are disabled.
</Alert>

Change Secrets rotates the credentials of accounts stored in JumpServer. A change-secret task can run immediately or on a schedule, generate a specific or random secret, and notify recipients by email when it finishes.

A change-secret task authenticates through a privileged account on the asset, so the asset's account list must contain a working privileged account.

## Prerequisites

- Access to **PAM > Security > Change Secrets** with permission to view change-secret tasks.
- The target assets or nodes already exist. See [Assets](/features/console/assets/).
- Each target account has secret change enabled. See [Accounts](/features/console/accounts/).
- A privileged account is available on the asset and can authenticate to it.

## Overview

The page contains five tabs:

- **Overview** – summary counts, success and failure trend, and failed-account list.
- **Change secret tasks** – task definitions and schedules.
- **Execution history** – one row per run with status, duration, and log.
- **Execution records** – per-account results, with old and new secret access.
- **Change secret status** – in-progress changes, shown when the change-after-session setting is enabled.

## Create a change secret task

<Steps>

<div>
  <Nav name="pam" />
</div>

<div>
Open **Security > Change Secrets** and select **Change secret tasks**.
</div>

<div>Click **Create**.</div>

<div>In the **Name** field, type the task name.</div>

<div>
  In the **Accounts** field, type the usernames to rotate and press Enter after
  each.
</div>

<div>
  In the **Assets** and **Nodes** fields, select the targets. The two fields can
  be combined.
</div>

<div>
  Choose the **Secret strategy** (**Specific secret** or **Random generate**),
  the **Secret type** (**Password** or **SSH key**), and then supply the
  **Password**, **Private key**, and optional **Key password**, or the
  **Password rules** for random generation.
</div>

<div>
  Optionally configure **Parameters** for the platform, enable **Periodic** to
  schedule the task, keep **Check connection after change** enabled, leave
  **Active** selected, and add **Recipients** for email notification.
</div>

<div>Click **Submit**.</div>

</Steps>

## Secret types

A change-secret task sets one type of secret for the whole task, and the type must match the credential that the account stores on the asset:

- **Password** – the task sets the account password. With **Specific secret**, type the target value in **Password**. With **Random generate**, **Password rules** control the length and character requirements of the generated password.
- **SSH key** – the task sets the account's private key. With **Specific secret**, paste the new key in **Private key** and, if the key is encrypted, type its passphrase in **Key password**. **Key password** protects the private key file; it is not the password the account uses to sign in to the asset.

<Alert type="note">
  Random generation is documented for passwords through **Password rules**.
  Whether the same strategy can generate an SSH key pair is not confirmed. Some
  versions also provide a separate **SSH key strategy** setting that chooses
  between replacing only keys pushed by JumpServer and emptying the key and
  appending a new one; whether this version keeps that setting is not confirmed.
  Check the fields available in your build before planning a key rotation.
</Alert>

## Windows domain accounts (WinRM)

A change-secret task changes a secret by signing in to the asset and running the change there. For Windows assets, that management path is **WinRM** or **SSH (OpenSSH)**. A Windows host or Windows Active Directory platform can enable RDP, SSH, SFTP, VNC, and WinRM, but only SSH and WinRM provide the command channel that a change task needs. See [Connect assets](/features/workbench/web-terminal/asset-connection).

A Windows asset whose platform enables only **RDP** (or RDP and VNC) cannot run a change-secret task, because those protocols open a graphical session and give the task no channel to execute the password change. To rotate its accounts, enable **WinRM** or **OpenSSH** on the platform and on the asset, then confirm that the privileged account can sign in over that protocol. **Parameters** do not help here, because they apply to AIX, Linux, and Unix assets only.

Domain accounts are added to the task by username in **Accounts**, like local accounts. The privileged account that runs the task must be able to authenticate to the asset and change the target account; whether it must be a domain account with directory rights is not confirmed, so do not assume that a local administrator works for every domain account.

<Alert type="note">
  The following Windows and domain details are not confirmed in this
  documentation: the accepted way to write a domain account in **Accounts** (for
  example `DOMAIN\user` versus `user@domain`), which account types a task can
  cover (local, domain, or both), the role the changing account needs on the
  domain controller, and the version in which Windows domain account change was
  introduced. Verify them on your deployment before relying on this page.
</Alert>

## Required permissions

A change-secret task signs in to the asset with one account and changes the secret of another. The changing account must already exist on the asset and be able to authenticate over the protocol the task uses, such as WinRM or SSH on Windows. It is not the account whose secret is being changed, and JumpServer does not create it for you.

Give the changing account only the rights it needs to reset the target account's secret. Which rights those are is decided by the target platform and by your directory policy, so the minimum set differs between platforms.

<Alert type="note">
  For Windows domain accounts, whether a delegated password-reset permission is
  enough or a directory administrator right such as **Domain Admins** is
  required is not confirmed in this documentation. Confirm it with your identity
  team before granting rights beyond your normal least-privilege baseline. The
  account that runs a task is itself excluded from rotation by default; see
  [Limitations](#limitations).
</Alert>

## LDAPS alternative

Some environments reset Windows domain passwords through an LDAP or LDAPS connection to a domain controller instead of signing in to each Windows asset. This page documents only the WinRM and SSH (OpenSSH) change paths. Whether JumpServer provides an LDAPS-based change channel is not confirmed.

<Alert type="note">
  Whether an LDAPS change channel exists, how it would be configured, and which
  edition or version would provide it are not confirmed. Until these points are
  verified, plan Windows domain rotation around WinRM or OpenSSH and the
  prerequisites in [Windows domain accounts](#windows-domain-accounts-winrm).
</Alert>

## Limitations

<Alert type="warning">
  By default JumpServer does not change the secrets of privileged accounts, nor
  of accounts named `root` or `administrator`, and it excludes the privileged
  account used to run the task. To allow privileged-account rotation, set
  `CHANGE_AUTH_PLAN_SECURE_MODE_ENABLED=false` in the configuration file and
  restart the JumpServer service.
</Alert>

Because this changes a high-risk credential, use a separate, controlled task for privileged accounts and test it on a non-production asset first.

- **Accounts with a switch-from relationship:** Do not place accounts that share a _switch from_ relationship on the same asset into one task. Split them into two tasks and rotate them separately, because the first change can invalidate the account that the second change depends on.
- **Parameters are platform-specific:** **Parameters** apply to AIX, Linux, and Unix assets only. They do not apply to Windows assets and cannot work around a missing WinRM or OpenSSH channel.
- **Asynchronous execution:** Change-secret tasks run in the background through celery and ansible. If a task stays queued or shows `....` instead of a result, open **Job Center > Task Monitoring** and check that celery and ansible are **Online**; restart `jms_celery` if either is offline. See [System tasks](/features/system-settings/infrastructure/system-tasks) and [Troubleshooting](/operations/troubleshooting).

<Alert type="note">
  Three behaviours are not confirmed in this documentation: whether accounts in
  the Windows **Protected Users** security group can be rotated, whether a task
  that fails partway rolls the account back to its previous secret or leaves it
  with the new one, and which account and permissions the **Check connection
  after change** verification uses. The old and new secrets of a record remain
  available in **Execution records** after MFA verification, so keep the record
  before rotating the account again, and test failure handling on a
  non-production asset first.
</Alert>

## Run and review

Use the green run button in the row, or open the task and use the manual execution action, to start a change. The **More** menu provides **Edit**, **Delete**, and **Duplicate**.

The **Overview** tab summarizes today, the last 7 days, or the last 30 days: task counts (total, periodic, asset management), execution counts (total, success, failed), and running changes. The **Account secret change success/failure** chart plots success against failure, and the failed-account list shows each failure with its error.

**Execution records** lists the changed accounts with asset, username, end date, success, test, and error. Opening a record requires MFA verification before the old and new secrets are shown, and a failed change can be retried from there.

## Application credential rotation

<VersionBadge version="5.2.0" />

Application credential rotation maintains a pair of accounts for an application
and switches between them instead of changing a single credential in place. A
rotation alternates the primary and standby accounts, switches the accounts across
the affected assets, and records the execution history. The client reports the
current status so you can confirm which account is active after a rotation.

Use this mode when an application cannot tolerate a window in which its only
credential is invalid. Review the execution history after each rotation and
confirm that the standby account is reachable before the next run.
