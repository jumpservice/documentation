# Troubleshooting

Most operational problems show up as a component that will not start, a page that
returns an error, or a connection that fails. Work from the outside in: confirm the
service state, read the component logs, then check the configuration the failing
component depends on. This page lists the first checks and the most common causes.

## First checks

```sh
./jmsctl.sh status
./jmsctl.sh tail
```

Then confirm that Core is healthy:

```sh
curl -s http://127.0.0.1/api/health/
```

`/api/health/`, `/koko/health/`, and `/lion/health/` return the component state and
are also what a load balancer should check.

## Where the logs are

Component logs are written under `VOLUME_DIR`, `/data/jumpserver` by default:

| Component | Container | Log directory |
| --- | --- | --- |
| Core | `jms_core` | `/data/jumpserver/core/data/logs` |
| Celery | `jms_celery` | `/data/jumpserver/core/data/logs` |
| KoKo | `jms_koko` | `/data/jumpserver/koko/data/logs` |
| Chen | `jms_chen` | `/data/jumpserver/chen/data/logs` |
| Razor | `jms_razor` | `/data/jumpserver/razor/data/logs` |
| Magnus | `jms_magnus` | `/data/jumpserver/magnus/data/logs` |
| Web | `jms_web` | `/data/jumpserver/nginx/data/logs` |

Core writes `jumpserver.log`, `gunicorn.log`, `drf_exception.log`, and
`unexpected_exception.log`. Read the files directly, or use Docker:

```sh
tail -f /data/jumpserver/core/data/logs/jumpserver.log
docker logs --since 30m jms_core
```

The detail level is controlled by `LOG_LEVEL`. `docker logs` output disappears when
the container is recreated, so copy important log files aside before an upgrade.

## Common problems

| Symptom | What to check |
| --- | --- |
| Web UI returns 400 or 403 | `DOMAINS` must contain the exact host or IP users open in the browser; restart after editing |
| Web UI returns 502 or 504 behind a proxy | Proxy health checks, WebSocket upgrade headers, and the backend port |
| Services do not start | `./jmsctl.sh status`, `docker ps`, and the Core log; check disk space under `VOLUME_DIR` |
| Asset connection fails | Authorization to the asset and account, account secret validity, connectivity test, platform protocol settings, and the zone gateway if the asset is behind one |
| Web Terminal or web assets do not load | KoKo health, port `2222` for SSH client access, and port `5001` for the web proxy |
| Login fails after enabling MFA | Server time drift (configure NTP) and the user's MFA secret; an administrator can reset MFA |
| Database or Redis connection errors | `DB_USE_SSL` / `REDIS_USE_SSL` and certificate files, service availability, and credentials |
| Recordings cannot be played | Video Worker state for graphical sessions, storage connectivity, and free space on `VOLUME_DIR` |
| Jobs or discovery tasks keep failing | Target host reachability, account permissions on the target, and the task log |

## Use the audit trail

For user or administrator reports, correlate the time of the issue with the audit
records in **Audits > Operation logs**, **Login logs**, and **Asset sessions**. The
operation log shows who changed which object, while the session record shows what
happened during the connection.

## Before contacting support

Collect the following in one archive:

1. Output of `./jmsctl.sh status` and `./jmsctl.sh --help`.
2. The JumpServer version from the UI or the installer output.
3. Core, KoKo, and web logs around the failure time.
4. The browser error, the failing URL, and the user, asset, and time involved.
5. A screenshot of the failing page, without secrets.

See the [Client documentation](/features/client/) page for connection-specific
issues.
