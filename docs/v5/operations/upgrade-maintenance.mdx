# Upgrade & Maintenance

JumpServer releases new versions regularly. Upgrading keeps the platform on
supported components and security fixes, while routine maintenance keeps the
database, storage, and logs from degrading over time. This page covers the upgrade
path, the preparation steps, the upgrade commands, and the recurring tasks an
operator should schedule.

## Supported upgrade path

Upgrade along the following path to avoid incompatible schema changes:

- **v2 to v3**: the two versions differ significantly. Read the upgrade notes
  before starting.
- **v3 to v4**: first upgrade to the latest v3 release, then to v4.
- **v4 to v5**: database migrations roll forward continuously, so any v4 release can
  be upgraded to v5. For early v4 releases, upgrade to the latest v4 release first.

The detailed step-by-step upgrade for both installation types is in the
[Upgrade](/upgrade) guide.

## Before the upgrade

1. Read the release notes of the target version for behavior changes and new
   requirements; pay attention to the database and Redis version requirements.
   V5.2.0 bundles PostgreSQL 18.7 and Redis 8.10.3, and migrates a bundled
   PostgreSQL 10 to 17 installation automatically during a standard upgrade.
2. Schedule a maintenance window. Upgrading stops the services and interrupts
   active sessions.
3. Back up the database and static files. See
   [Backup & Restore](/operations/backup-restore). A routine database backup
   failure shows a 30-second confirmation prompt during the upgrade; a backup
   required for a PostgreSQL major version migration is still mandatory.
4. Confirm that `DOMAINS` contains the domain or IP address users open in the
   browser. A missing trusted host is the usual cause of 400 and 403 responses after
   an upgrade.
5. Keep the current packages and configuration backup until the new version has
   been verified.

## Upgrade an offline installation

```bash
cd /opt
tar -xf jumpserver-ce-<version>-x86_64.tar.gz
cd jumpserver-ce-<version>-x86_64
./jmsctl.sh upgrade
./jmsctl.sh start
```

For the enterprise offline package, use the `jumpserver-ee-<version>-x86_64`
package and the same commands.

## Upgrade an online installation

Download the installer package for the target version, extract it, then upgrade:

```bash
cd /opt
tar -xf jumpserver-installer-<version>.tar.gz
cd jumpserver-installer-<version>
./jmsctl.sh upgrade
./jmsctl.sh start
```

## After the upgrade

- Run `./jmsctl.sh status` and confirm that all expected containers are running.
- Open `/api/health/` and the web UI, then log in as a normal user.
- Check the version shown in the UI and in the startup output.
- Test one connection, one recording playback, and one account secret to confirm
  that the data survived the migration.
- Watch the Core and protocol component logs for errors for a few minutes.
- Upgrade the other node in a high-availability pair after the first node is
  healthy.

The checklist below expands these checks and adds the ones that are easy to skip,
such as component registration and audit continuity.

## Upgrade verification checklist

Verify the deployment in this order before you declare the upgrade complete. Each
check validates a different layer, so do not skip one because the previous check
passed.

| #   | Check                  | Where                                             | Pass condition                                                             |
| --- | ---------------------- | ------------------------------------------------- | -------------------------------------------------------------------------- |
| 1   | Service state          | `./jmsctl.sh status`                              | Every expected container is running                                        |
| 2   | Component registration | **System Settings > Components**                  | Each enabled component instance registers and reports a normal state       |
| 3   | Core health            | `curl -s http://127.0.0.1/api/health/`            | The health endpoint reports the expected state                             |
| 4   | Sign-in                | Web UI                                            | A normal user and an administrator can both sign in                        |
| 5   | Protocol connectivity  | **Workbench** or a test authorization             | One session per protocol you use opens end to end                          |
| 6   | Recording playback     | **Audits > Asset sessions > Historical sessions** | A recording made after the upgrade plays, and an older one still plays     |
| 7   | Audit continuity       | **Audits**                                        | Login, operation, and session records from before and after are present    |
| 8   | Enterprise license     | **System Settings > License**                     | The license is valid and licensed features remain available                |
| 9   | Scheduled tasks        | **Job Center** or **System Tasks**                | A scheduled task runs after the upgrade                                    |
| 10  | User email uniqueness  | **Console > Users**                               | No duplicate email addresses remain; `.invalid` placeholders are corrected |

See [Components](/features/system-settings/infrastructure/components) for the
component states and [Asset sessions](/features/audits/sessions/asset-sessions)
for replay conditions.

## Rollback preparation

Prepare the rollback before you start the upgrade, not after a check fails.

- **Backup point.** Run `./jmsctl.sh backup_db` before the upgrade, verify that the
  dump file is readable and complete, and copy it off the host. A backup that only
  exists on the host being upgraded is not a rollback point. See
  [Backup & Restore](/operations/backup-restore).
- **Version anchor.** Keep the current installation package, its configuration,
  and the database backup together, so that the restored database matches the
  package you return to.
- **Rollback triggers.** Roll back when a verification check cannot be met and the
  cause is not a configuration value that you can correct, for example when Core
  does not start after the upgrade, component registration cannot be restored, or
  session recordings and audit records are missing.
- **Rollback steps.** Stop the services, restore the pre-upgrade database backup,
  return to the package that matches that backup, and start the services. Follow
  the restore procedure in [Backup & Restore](/operations/backup-restore); when the
  restore reports table conflicts, follow the restore guidance in the
  [FAQ](/reference/faq).
- **After a rollback.** Record the failed check and the collected logs, and report
  them before you retry the upgrade.

## Routine maintenance

| Task                            | Frequency     | Notes                                                                                   |
| ------------------------------- | ------------- | --------------------------------------------------------------------------------------- |
| Database and static file backup | Daily         | Copy backups off the host; verify restore regularly                                     |
| Disk usage of `VOLUME_DIR`      | Weekly        | Recordings and logs grow quickly; increase storage or move recordings to object storage |
| Log review                      | Weekly        | Check Core, KoKo, and web logs for repeated errors                                      |
| Certificate renewal             | Before expiry | Configure HTTPS and renew under `config/nginx/cert`                                     |
| License validity                | Before expiry | Enterprise licenses expire; upload a new license file in System Settings                |
| Patch and version updates       | Per release   | Follow the upgrade path above                                                           |

Local cleanup of login, operation, and file-transfer records is configured under
**System Settings > System Tasks > Regular clean-up**. Recordings and commands
written to external storage are not affected by that page. See
[System Tasks](/features/system-settings/infrastructure/system-tasks) and
[Storage](/features/system-settings/infrastructure/storage).
